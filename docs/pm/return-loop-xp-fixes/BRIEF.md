# Brief — return-loop-xp-fixes: experience is awarded once, and a failed score is retried

## Goal (in play)
When a session ends, the experience it earned lands exactly once, the level that comes with it agrees with the total, and claiming rewards never adds the same experience a second time. If the scoring call fails at session end, the session still ends and the player can still come back — and the held award is retried at the next session start instead of being lost for good.

## Background
- Source job: the return-loop test suite, built and PM-verified 2026-11-26 (commit `ab52d37`, version 1.0.221; report `docs/pm/reports/return-loop-REPORT.md`). Its gate is red-with-cause, confirmed by Zach 2026-11-26: exactly 9 failing assertions covering 7 product gaps, no new failures. This job fixes the first two gaps only. The other five gaps stay red, exactly as named in that report.
- Gap 1 — the session's experience is awarded twice. At session end the orchestrator already adds the experience (`server/services/sessionEndService.js:43` → `server/services/xpService.js:158`) and also stores it as `rewards.xp`. The claim-rewards route adds `rewards.xp` again (`server/routes/dmSession.js:4547`). The level is not recomputed at claim, so the experience total and the level disagree. The claim route also gives every active class-based companion the same experience (`dmSession.js:4589-4591`); the return-loop report notes this may be intended, since it is the companions' only award. Failing assertion: `[return] GAP G-1: the session's XP is awarded once — claiming does not add it again (XP after end 3791, after claim 4883, award 1092)`.
- Gap 2 — a failed experience score is never retried. When the scorer call fails, the stage is marked `failed` (`sessionEndService.js:47-50`); `pending_llm` is set only when no model function is passed at all (`:37-40`), and the route always passes one. Nothing outside `sessionEndService.js` reads `session_end_runs`, so nothing retries at the next start and the session's experience is lost. The other half of the design already holds and is asserted: the session ends normally and the return is not blocked. Failing assertion: `[protect] GAP G-2: the held XP award is retried at the next session start (stage failed, XP 2699 → 2699)`.
- Surveyed call chain (from the return-loop report, live bytes at `ab52d37` — verify against live bytes before trusting): session end is `POST /api/dm-session/:id/end` (`dmSession.js:3762`); rewards analysis at `:3812-3832`; orchestrator `endSession(...)` at `:3862-3868` → `sessionEndService.js:120-131`; experience stage at `sessionEndService.js:32-52` → `awardSessionXP` writes `experience`, `level` and `level_up_pending_choices` at session end (`xpService.js:142-160`); claim rewards refuses play while a completed session is unclaimed (`dmSession.js:4525`, refusal at `:537-547`); session start is `POST /api/dm-session/start` (`dmSession.js:508`).
- Settled decisions that shape this job (do not re-decide): level at session end, never mid-combat (experience system, locked 2026-10-19); experience scoring itself is locked — session-end scoring across combat/exploration/quests/discovery/social, no per-kill experience, breadth bonus and pace bands as built; the 9 return-loop gap checks stay real, failing assertions and are never edited to pass (PM decision, Muse, 2026-11-25, confirmed at the gate 2026-11-26) — a gap check turns green only because the product fix makes it pass; testing (Zach, 2026-11-24): no browser test per job, one test once everything is done, per-job gate is Zach's full `npm test` only; the PC is the only working copy (Zach, 2026-11-13).
